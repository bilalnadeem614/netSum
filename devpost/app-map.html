netSum app map

A personal finance PWA that will not close a day until the balances you count match the balances it calculates.

The three pieces

  • React app (frontend/): screens, forms and charts. Holds no money rules.
  • FastAPI backend (backend/app/): calculates balances and runs the day-close gate. The rule lives only here.
  • Supabase Postgres: tables for methods, expenses, logs, closed days, loans, savings and the goal. Balances are never stored; they are calculated from logs.

One action: tap "Close day"

Reference route (not toured live)

  1. frontend/src/pages/CloseDay.jsx, search async function close: posts the typed real balances to /close-day, and on a 409 stores the per-method differences (setDiff) so those rows turn red.
  2. backend/app/routes/days.py, search def close_day: loads the open day, calculates balances, calls balances.differences. Any difference raises HTTPException(409, ...) and nothing is written. If all match, it inserts one row into days.
  3. backend/app/balances.py, search def differences: compares real and calculated with exact Decimal values. def calculated and def opening above it build the calculated balance from the previous closed day plus the day's logs.

To change this, start here

  • What counts as a match (for example, a small tolerance): differences() in backend/app/balances.py, then update backend/tests/test_close_gate.py.
  • How the close screen looks: frontend/src/pages/CloseDay.jsx and .close-row in frontend/src/styles.css.
  • Colours or the light/dark theme: the tokens at the top of frontend/src/styles.css.
  • A new table or field: backend/schema.sql (run it in Supabase), then the matching route in backend/app/routes/.
  • Database connection behaviour: backend/app/db.py (one client per thread, see below).

A practice to reuse

Check the behaviour that can fail, not just the code that passes

The close-day rules have unit tests in backend/tests/test_close_gate.py (a match closes, a mismatch reports the difference, 0.10 + 0.20 stays exact, the next day opens at the previous real balance). Those tests passed throughout.

Speeding up /api/home by running its queries in parallel passed every test and was verified by comparing the JSON before and after. In real use it still returned 500s, because the threads shared one Supabase HTTP/2 connection. The failure only showed under concurrent requests. The fix was one client per thread in backend/app/db.py, and the check that confirmed it was 90 simultaneous requests returning 200.

On another project: when a change affects how things run together (threads, caches, connections), write down the condition that could break it and test that condition directly, in addition to the unit tests.

Run it again

  • Backend: cd backend && uvicorn app.main:app --reload (needs backend/.env, see .env.example).
  • Frontend: cd frontend && npm run dev, then open http://localhost:5173.
  • Tests: cd backend && pytest.
